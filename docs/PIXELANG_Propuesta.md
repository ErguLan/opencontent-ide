## **1. Resumen Ejecutivo** 

**PIXELANG** es un nuevo lenguaje de descripción visual (DSL) diseñado específicamente para que agentes de inteligencia artificial de texto — como Claude, Kimi, DeepSeek, Qwen y otros modelos sin capacidad nativa de generación de imágenes — puedan crear arte visual de alta calidad mediante código declarativo. 

### **El Problema** 

Los agentes de IA de texto, cuando intentan generar imágenes mediante código, se ven forzados a usar herramientas inadecuadas: 

- **HTML/CSS** →diseñado para layout web, no para arte 

- **SVG** →vectorial puro, sin capacidad de raster realista 

- **Canvas 2D** →API imperativa que los LLMs no razonan bien 

- **Pillow/Cairo** →APIs técnicas para humanos, no semánticas para IA 

El resultado: “palos y ramas”, formas primitivas, colores planos, cero realismo. 

Generated by Kimi 

### **La Solución** 

PIXELANG introduce **primitivas semánticas de primera clase** donde los conceptos visuales (materiales, iluminación, estilos, composición) son elementos nativos del lenguaje. El agente de IA “describe” visualmente con precisión estructurada, y un runtime especializado traduce esas descripciones a matemáticas gráficas avanzadas. 

### **Diferenciador Clave** 

No competimos con DALL-E o Midjourney en velocidad o costo. Competimos en **control, editabilidad, privacidad y democratización** . PIXELANG permite que cualquier agente de texto, incluso el más modesto, genere arte visual sin depender de APIs externas ni modelos de difusión masivos. 

## **2. Diagnóstico del Problema Actual** 

### **2.1 Por qué los agentes de IA fallan al generar imágenes mediante código** 

### **HTML/CSS: Un lenguaje de LAYOUT, no de ARTE** 

- Diseñado para organizar contenido web, no para pintar 

- Los modelos generan “palos y ramas” porque eso es todo lo que CSS puede hacer nativamente 

- No hay primitivas para textura, luz, sombra realista, materialidad 

- Las sombras son box-shadow planas, no simulación de física de luz 

### **SVG: Vectorial puro, sin alma raster** 

- No puede simular ruido orgánico, grain fotográfico, imperfecciones naturales 

- Las sombras son filtros primitivos (feGaussianBlur, feDropShadow) que no simulan física de luz real 

- No hay concepto de “material” (piel, metal, tela, hojas con translucidez) 

- Todo es matemáticamente perfecto — la naturaleza es imperfecta 

### **Canvas 2D: Imperativo y mutable** 

- Requiere secuencias de comandos imperativos (moveTo, lineTo, fill, stroke) 

- Los LLMs no razonan bien sobre estado gráfico mutable 

- No hay abstracciones de alto nivel para “un rostro humano realista” o “una hoja de roble con venas pinnadas” 

- Cada píxel requiere coordenadas exactas — los LLMs son malos en geometría de bajo nivel 

### **Librerías existentes (Pillow, Cairo, Skia): APIs técnicas, no semánticas** 

- Diseñadas para programadores humanos, no para ser “escritas” por IA 

- Requieren conocimiento de coordenadas exactas, matrices de transformación, buffers de memoria 

- No tienen conceptos de “estilo impresionista”, “iluminación dorada de atardecer”, “textura de óleo en lienzo de lino” 

### **2.2 El gap fundamental** 

**Los LLMs razonan en CONCEPTOS, pero las APIs gráficas operan en PIXELES.** 

Generated by Kimi 

Un LLM entiende perfectamente: _“un rostro con sombra suave bajo luz cálida de atardecer, piel con poros finos y un toque de translucidez en las mejillas”_ . 

Pero no puede traducir eso a: 

ctx.fillStyle = '#F5D0C5'; ctx.beginPath(); ctx.ellipse(150, 200, 40, 50, 0, 0, Math.PI*2); ctx.fill(); 

### **La traducción conceptual →pixel es donde todo se rompe.** 

Los agentes de IA en 2026 siguen teniendo un gap crítico documentado: _“They can’t create media. No images, no videos, no diagrams. When your agent plans a beautiful architecture diagram, it can describe it. It can’t produce it.”_ 

## **3. Análisis de Mercado: ¿Por qué nadie lo ha resuelto?** 

### **3.1 Razones Técnicas** 

**La industria se obsesionó con los Modelos de Difusión** DALL-E, Midjourney, Stable Diffusion, 

FLUX, Imagen 4 — todos siguen el mismo paradigma: 

- Entrenar una red neuronal de 10B+ parámetros para generar pixeles directamente 

- No requiere que el LLM “entienda” gráficos, solo que describa lo que quiere 

- **Problema** : Requiere GPUs masivas, no es accesible para agentes de texto puro, es una caja negra ineditable 

**Los agentes de texto no tienen capacidad nativa de generación visual** 

- No pueden ejecutar código Python con PIL de forma nativa en su entorno sandbox 

- No tienen acceso a renderizadores gráficos 

- Están diseñados para razonamiento, no para computación gráfica 

### **El problema es INTERDISCIPLINARIO** 

- Los ingenieros de gráficos por computadora no piensan en LLMs 

- Los ingenieros de LLMs no piensan en gráficos procedurales 

- Los diseñadores de DSL no piensan en generación automática por IA 

- **Nadie ha atacado el problema holísticamente** 

### **La complejidad del realismo es ENORME** 

- Simular luz, sombra, textura, subsurface scattering, reflexión, refracción… 

- Requiere shaders, ray tracing, o rasterización avanzada 

- Ningún lenguaje simple puede capturar esto sin volverse tan complejo como HLSL/GLSL 

### **3.2 Razones de Negocio** 

### **Las APIs de imagen son negocios rentables** 

- DALL-E 3, Midjourney, FLUX API cobran por cada imagen generada 

Generated by Kimi 

- ¿Por qué resolver un problema difícil cuando puedes cobrar por API? 

- Las empresas prefieren vender acceso a modelos de difusión que crear infraestructura abierta 

### **No hay demanda aparente del mercado masivo** 

- Los usuarios finales quieren “escribir prompt →obtener imagen” 

- No quieren “escribir código →obtener imagen” 

- **PERO** : El mercado de “agentes de IA que necesitan generar imágenes sin API externa” es nicho pero CRECIENTE RÁPIDAMENTE 

### **El open source en gráficos procedurales está fragmentado** 

- Processing, p5.js, Three.js, ShaderToy… cada uno es su propio ecosistema 

- No hay un estándar unificado que un LLM pueda aprender fácilmente 

- No hay un “HTML para la generación de imágenes por IA”

## **4. La Propuesta: PIXELANG** 

### **4.1 Filosofía Central** 

**“Un lenguaje donde los CONCEPTOS VISUALES son primitivas de primera clase, no derivados de geometría básica.”** 

### **4.2 Analogía poderosa** 

- **HTML/CSS** es como intentar escribir una novela usando solo un diccionario de 100 palabras 

- **PIXELANG** es como darle al escritor un vocabulario literario completo con metáforas, estilos, y técnicas narrativas 

### **4.3 Principios de Diseño** 

1. **Declarativo, no imperativo** — El agente describe QUÉ quiere, no CÓMO dibujarlo 

2. **Semántico, no geométrico** — “rostro humano” es una primitiva, no una colección de elipses 

Generated by Kimi 

3. **Jerárquico y modular** — Escenas contienen sujetos, sujetos contienen materiales, materiales contienen propiedades físicas 

4. **Estilo-agnóstico** — El mismo código puede renderizarse en fotorealismo, cartoon, óleo, o acuarela 

5. **Procedural por defecto** — Todo detalle se genera matemáticamente, no se almacena en texturas estáticas 

6. **LOD para IA** — Niveles de detalle adaptativos: sketch, concept, production, photorealistic

### **6.2 Especificación de Capas** 

### **Capa 1: El Parser de PIXELANG** 

- **Input** : Código PIXELANG (texto plano, sintaxis inspirada en CSS/JSON/YAML) 

- **Output** : AST (Árbol de Sintaxis Abstracta) semántico 

- **Implementación** : 

   - MVP: Python con Lark o PLY 

   - Producción: Rust con nom o pest para velocidad 

- **Features** : 

   - Tipado estático de propiedades visuales 

   - Herencia de estilos 

   - Macros y templates reutilizables 

   - Validación semántica (“¿existe el material ‘hoja_roble’?”) 

### **Capa 2: El Motor de Interpretación Semántica** 

- Traduce conceptos de alto nivel a primitivas de renderizado 

- Sistema de plugins para nuevas primitivas 

- Cache de materiales y meshes procedurales 

- Resolución de dependencias (un material puede referenciar otro) 

### **Capa 3: El Renderizador Híbrido** 

- **Backend GPU** : Vulkan / Metal / DirectX / WebGPU 

- **Técnicas** : 

   - PBR (Physically Based Rendering) para realismo 

   - NPR (Non-Photorealistic Rendering) para estilos artísticos 

   - Deferred shading para múltiples luces 

   - Screen-space reflections y ambient occlusion 

   - Volumetrics para niebla, rayos de luz, nubes 

- **Output** : PNG, JPEG, EXR, WebP 

Generated by Kimi 

### **Capa 4: El Runtime de Agentes**

## **7. ¿Por qué esto funcionaría?** 

### **7.1 Lógica Inversa: El Truco Maestro** 

**No hacer que el LLM “dibuje”, sino que “describa visualmente con precisión estructurada”** 

Los LLMs son **EXCELENTES** describiendo. Son **MALOS** calculando coordenadas. Entonces: 

1. **Damos al LLM un vocabulario visual rico** — como un director de arte hablando con un equipo de VFX 

2. **El runtime traduce descripciones a matemáticas** — como el equipo de VFX que ejecuta la visión 

3. **El LLM itera en conceptos, no en píxeles** — “más sombra dramática”, “piel más pálida”, “hojas más otoñales” 

### **7.2 Analogía con la revolución de los compiladores**

|Era|Programador escribe|Compilador traduce a|
|---|---|---|

|Después|C/Python (alto nivel)|Assembly|
|**PIXELA**|**NG**PIXELANG (conceptos visuales)|Shaders/Renderizado (bajo nivel)|



### **7.3 Astucia: Entrenamiento Híbrido** 

No necesitamos entrenar un modelo de difusión de 10B parámetros. Necesitamos: 

1. **Dataset de pares** : (descripción visual detallada, código PIXELANG) 

2. **Fine-tuning ligero** de un LLM existente (7B-13B parámetros) para que genere PIXELANG 

3. **Runtime como software tradicional** (no ML), optimizado y rápido 

**Esto es órdenes de magnitud más barato y accesible que entrenar un modelo de difusión.**
