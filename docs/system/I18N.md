# i18n System (`src/i18n/`)

## Summary

Dot-notation translations with `{variable}` interpolation, served in English and Spanish from a key tree that is assembled from four files at load time.

**For conventions, parity rules and how to add a language, read `docs/TRANSLATION_SYSTEM.md`.** This document describes the runtime API.

## Files

```
src/i18n/
├── index.js                 # deepMerge, t(), setLanguage(), getSection(), getLanguages()
├── en.json                  # English base tree (693 leaf keys)
├── es.json                  # Spanish base tree (693 leaf keys, exact parity)
├── artifactTranslations.js  # { en, es } -> { artifactStudio }
└── uxTranslations.js        # { en, es } -> { landing, workspace, setup, library, ux, cliUx }
```

`src/context/LanguageContext.jsx` holds the React language state and exposes `useLanguage()`.

## Assembly

```js
const translations = {
    es: deepMerge(es, artifactTranslations.es, uxTranslations.es),
    en: deepMerge(en, artifactTranslations.en, uxTranslations.en)
};
```

Later layers win for scalar values. Each merged tree resolves to 862 leaf keys.

## API

### `t(key, vars?, lang?)`

```js
import { t, setLanguage } from '../../i18n';

setLanguage('en');
t('common.close');                            // -> "Close"
t('common.close', {}, 'es');                  // -> "Cerrar"
t('delivery.library.stateEmptyTitle', { state: 'borrador' });
t('nonexistent.key');                         // -> "nonexistent.key"
```

- Traverses the tree by dot-separated segments.
- Interpolates `{varName}` when a `vars` object is supplied. An unknown `{varName}` is left as written rather than becoming `undefined`.
- Falls back to the current language, then to Spanish.
- Returns the key itself when the key does not resolve, or when it resolves to a non-string.
- Falls back to Spanish when the requested language is not loaded.

### `setLanguage(lang)`
Sets the module-level current language. An unknown code is ignored.

### `getLanguage()`
Returns the current language code.

### `getSection(section, lang?)`
Returns a whole section object, or `{}`. This is how array-valued keys such as `landing.placeholderHints` are read, since `t()` only returns strings.

### `getLanguages()`
```js
[
    { code: 'es', name: 'Espanol', flag: 'ES' },
    { code: 'en', name: 'English', flag: 'EN' }
]
```

### `getBrowserLanguage()`
Maps `navigator.language` to a loaded code, defaulting to `es`.

The module-level default is `'es'`. `LanguageContext` decides the initial language and calls `setLanguage`.

## Using in Components

```jsx
import { useLanguage } from '../../context/LanguageContext';

function MyComponent() {
    const { t, language, languages, changeLanguage } = useLanguage();
    return (
        <div>
            <h1>{t('app.name')}</h1>
            <button onClick={() => changeLanguage('es')}>ES</button>
        </div>
    );
}
```

`useLanguage()` returns `t`, `language`, `languages` and `changeLanguage`. This is the canonical way to reach translations. Importing `t` directly from `src/i18n` is for code outside React — services, the CLI and the agentic pipeline. The pipeline receives `t` as a parameter rather than importing it, so it carries no language state.

## Parity

`en.json` and `es.json` are verified at 693 leaf keys each, with no key present in one and absent from the other. Every literal `t('…')` call across the 130 `.js`/`.jsx` files under `src/` resolves to a string in both merged trees.

The two exceptions are intentional: `landing.placeholderHints` is an array read through `getSection`, and `src/i18n/index.test.js` asserts on a deliberately missing key.

## Avoid

- Hardcoded user-facing strings in JSX.
- A key added to one language only.
- Showing a raw translation key as user-facing text; `t()` returning the key means the key is missing.
- Adding a key to `en.json` that `uxTranslations` also defines — the later layer wins and the edit has no effect.
